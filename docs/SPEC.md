- Backlog management
	- Manage as list of tickets
	- Each ticket has a unique number
		- Project - short acronym or abbreviation (eg. MSC for micro-security-cam)
            - Use `UNS` for unsorted 
			- Allow moving tickets between projects (update project prefix and reassign serial number)
		- Per-project serial number, minimum 3 digits, zero padded, starts at 001
	- Ticket type (Epic, Story, Bug, Spike)
	- Ticket status
		- Open = feature/bug fix described
		- Groomed = approach has been assessed, code and test updates identified, validation plan
		- In progress = branch created, effort underway, should be transient but may be useful for recovery
		- Ready for review = PR or report up for human approval
		- Complete = PR merged or report complete (for Spike)
		- Rejected
	- Links to other tickets
		- Mainly parent/child links for epics
		- Can link bug tickets or investigations to features
	- In general epics represent large multi-feature plan
- Sprints
	- Effectively a short-term todo list
	- Sequentially number them, year prefix, eg 2601, 2602, etc.
	- Contain list of tickets, can be any type but will mostly contain Story, Bug, and Spike)
	- Date tracking
		- Planned start (date)
        - Planned duration (days)
		- Actual start (date)
		- Actual finish (date)
	- To finish, all tickets must be done
		- Can push tickets out to another sprint
    - Tickets can be assigned to only one sprint
- User interface
    - Web based
    - Backlog view - filter by project, ticket type, status, date, etc.
    - Sprint view - status of ticket in sprint
    - Plan view - list of tickets by sprint, showing calendar duration for the sprints

- Other
    - Data must be stored on the local filesystem in a consolidated way to support backups
    - Deployable via script or simple tool that manages dependencies, takes in user configuration (such as the port to run the web server on, where to store state data, etc.
